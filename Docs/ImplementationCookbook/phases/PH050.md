# Phase Packet: PH050 — Interactive Approval Broker & Native Popup

## 1. Purpose
Implement the `ApprovalBroker` to handle sensitive action authorization requests (`PolicyDecision.ASK_USER`). Guarantees that any action requiring user confirmation is paused until explicitly approved via an independent native popup. Introduces single-use `ApprovalGrant(source="HUMAN_ALLOW_ONCE")` cryptographically bound to an immutable SHA-256 payload hash, atomic `consume_grant` under lock, and typed `ExecutionAuthorization` carrying `ProcessExecutionConstraints`. Fails closed on denial, timeout, popup crash, or capacity exhaustion. Establishes the initial `app/lifecycle.py` foundation.

## 13. Exact Algorithms / Security Invariants
1. **PENDING IS NEVER CONSUMABLE:** Only `ApprovalGrant` objects in `_grants` can be consumed. `PendingApproval` objects cannot execute.
2. **ATOMIC CONSUMPTION:** `consume_grant()` validates existence, expiry, and recomputes SHA-256 canonical hash under an `asyncio.Lock`. On mismatch, the grant is immediately invalidated and popped, returning `False`. On match, the grant is popped and returns `True`. Replay attempts return `False`.
3. **FAIL-CLOSED CAPACITY:** If pending requests reach `MAX_PENDING_APPROVALS = 10`, `request_decision` fails closed immediately with `PopupDecision.DENY`. It NEVER evicts an active pending approval.
4. **HUMAN APPROVAL HARD CONSTRAINTS:** Human approval NEVER bypasses permanent path denial, traversal checks, strict argv parsing, trusted executable resolution, or output limits.

## 14. Reference Implementation / Capsule Guidance
See `Docs/ImplementationCookbook/17_REFERENCE_CODE_CAPSULES.md#Capsule-1` (`CAP-001`) for the canonical `ApprovalBroker` implementation.

## 15. Concurrency Model
`asyncio.Lock` protects `_pending` and `_grants` collections. Popup subprocess launched via `asyncio.create_subprocess_exec` asynchronously without blocking loop.

## 16. Cancellation Behavior
When a request is cancelled via `asyncio.CancelledError`, any active popup child process is terminated immediately via SIGTERM/SIGKILL, state is purged from pending, and `asyncio.CancelledError` is re-raised.

## 17. Timeout Behavior
Hard 60.0-second timeout per approval request. If user does not respond within 60s, popup is closed and request fails closed with `PopupDecision.DENY`.

## 18. Retry / Idempotency Behavior
Approval requests and grant minting are strictly non-idempotent. Each request generates a unique UUID. Grants are consumed once atomically via `consume_grant()` and cannot be replayed.

## 19. Error Behavior
Fail-closed on all errors: subprocess execution failure, non-zero return code, malformed output, or timeout all result in `PopupDecision.DENY`.

## 20. Security Invariants
Immutable hash binding: grant is valid only for the exact canonical bytes of the approved `ActionRequest`. Hard security limits cannot be relaxed by user approval.

## 21. Resource Limits
Maximum 10 concurrent pending approval dialogs. Additional requests fail closed immediately with capacity exhaustion.

## 22. Secrets / Privacy Behavior
Sensitive request payloads are rendered in plain text for human confirmation; zero credentials, API keys, or raw tokens are stored in approval state.

## 23. Failure Cases / Edge Cases
- Popup process fails to launch: Fails closed to `PopupDecision.DENY`.
- User closes popup window without selecting Allow: Treated as `PopupDecision.DENY`.
- Timeout expires: Pending request popped; fails closed to `PopupDecision.DENY`; no grant is minted.
- Daemon restart / crash: All pending approvals and grants cleared from RAM; unexecuted actions cannot proceed.
